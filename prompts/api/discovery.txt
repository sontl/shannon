<systematic_approach>
Execute all phases below. Do not skip any phase.

## Phase 1: Schema Ingestion (PRIMARY — if schemas provided)

If schema URLs or files were provided above:
- **OpenAPI/Swagger:** `curl -s {{WEB_URL}}<schema-path> | jq .` Parse `paths`, `methods`, `parameters`, `requestBody`, `security`, `components.schemas`.
- **GraphQL:** Send introspection query:
  ```bash
  curl -X POST {{WEB_URL}}/graphql -H "Content-Type: application/json" \
    -d '{"query": "{ __schema { queryType { name } mutationType { name } types { name fields { name args { name type { name } } } } } }"}'
  ```
  Extract all queries, mutations, types, and argument shapes.

If NO schema provided, proceed to Phase 2 (dynamic discovery).

## Phase 2: Common API Path Discovery

Probe standard paths that APIs commonly expose:
- **Documentation:** `/api-docs`, `/swagger.json`, `/swagger/v1`, `/openapi.json`, `/v3/api-docs`, `/docs`, `/redoc`
- **GraphQL:** `/graphql`, `/gql`, `/api/graphql`, `/v1/graphql` (POST with introspection query)
- **Health/Meta:** `/health`, `/api/health`, `/status`, `/ping`, `/version`, `/metrics`, `/actuator/*`
- **Auth:** `/login`, `/api/auth/login`, `/oauth/token`, `/auth/register`, `/refresh`, `/logout`
- **Admin/Debug:** `/admin`, `/api/admin`, `/debug`, `/__debug__`, `/trace`
- **Common REST:** `/api/users`, `/api/v1/users`, `/api/v2/users`, probe resource nouns based on discovered schemas

For each path: `curl -sI -o /dev/null -w "%{http_code}\n" {{WEB_URL}}<path>`. Record responses that return 200, 201, 301, 302, 401, 403, 405 (real endpoints). Skip 404.

## Phase 3: HTTP Method Enumeration

For each discovered endpoint, test all standard methods to find hidden operations:
```bash
for m in GET POST PUT PATCH DELETE OPTIONS HEAD; do
  echo "$m: $(curl -s -o /dev/null -w "%{http_code}" -X $m {{WEB_URL}}<endpoint>)"
done
```

Use OPTIONS to reveal allowed methods and CORS config. Note any non-404 response on non-standard methods.

## Phase 4: Parameter Fuzzing

For each endpoint, discover parameters by:
- Inspecting schema (if available) for full parameter list
- Sending requests with common parameter names: `id`, `user_id`, `email`, `password`, `token`, `query`, `filter`, `page`, `limit`, `sort`, `include`, `format`
- Reviewing error responses — many APIs reveal expected fields in 400/422 error messages
- Testing for undocumented/debug parameters: `?debug=true`, `?admin=true`, `?test=1`, `?_format=json`, `?_method=DELETE`

## Phase 5: Response Analysis & Technology Fingerprinting

- Inspect response headers: `Server`, `X-Powered-By`, `X-AspNet-Version`, `Via`, `Set-Cookie` format
- Check response body structure: REST conventions, JSON:API, HAL, GraphQL errors
- Look for verbose error messages revealing stack traces, library versions, DB types
- Note rate limit headers: `X-RateLimit-*`, `Retry-After`, `X-Request-Id`

## Phase 6: Authentication Mechanism Detection

Identify auth without logging in:
- What does an unauthenticated request return? (401 vs 403 vs redirect)
- What `WWW-Authenticate` header value is returned?
- Are there login endpoints? Test with empty body to see expected format
- Is auth via Bearer token, session cookie, API key header, HTTP Basic, or OAuth2 flow?

## Phase 7: Prioritize Focus Areas

For each developer-hinted focus path, confirm it exists, document parameters, and note auth requirements.
