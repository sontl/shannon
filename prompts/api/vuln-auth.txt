- **Test the auth flow, not the users.** Focus on protocol flaws.

<systematic_approach>

## Phase 1: JWT Attacks (if JWT is used)

Decode the captured JWT (from auth-map). Test:

- **alg: none bypass**: Change header to `{"alg":"none","typ":"JWT"}`, remove signature
  ```bash
  UNSIGNED=$(echo -n '{"alg":"none","typ":"JWT"}' | base64 | tr -d '=' | tr '/+' '_-').$(echo -n '{"user_id":1,"role":"admin"}' | base64 | tr -d '=' | tr '/+' '_-').
  curl -H "Authorization: Bearer $UNSIGNED" {{WEB_URL}}/api/admin
  ```

- **Weak secret brute-force**: Use known weak secrets (`secret`, `secret123`, `jwt_secret`, `password`, app-name-derived strings)
- **HS256 vs RS256 confusion**: Sign HS256 token using RS256 public key as HMAC key
- **kid injection**: Manipulate `kid` header for SQLi or path traversal
- **Expired token acceptance**: Use a token past `exp` — is it still valid?
- **Audience/issuer bypass**: Forge tokens with different `aud`/`iss`

## Phase 2: Token Leakage

- Check if token appears in URL parameters (logs leak)
- Verbose error messages revealing token prefix
- Debug endpoints returning session/env data (`/api/debug`, `/api/config`)
- Referrer header leaks

## Phase 3: Password Reset Flow

If `/forgot-password`, `/reset-password` exist:
- Does reset token appear in response body? (Token leak)
- Is reset token predictable? (UUID v4 OK; timestamp-based BAD)
- Can you use the same token twice?
- Does the reset endpoint validate the account owner?
- Host header poisoning: does the reset link honor `Host:` header?

## Phase 4: Brute-Force & Rate Limit Testing

Send 3-5 rapid login attempts with wrong passwords.
- Is there rate limiting? (Should lock after N attempts)
- Does the error message differ between "user not found" and "wrong password"? (Username enumeration)
- Test `/register` with existing emails — does it reveal account existence?

## Phase 5: Session Management

- Session fixation: does token change on privilege change?
- Concurrent sessions: can the same token work in 2 places?
- Logout behavior: does server actually invalidate token?
- Refresh token: can you keep a refresh token forever? Is it rotated?

## Phase 6: MFA / 2FA Bypass (if MFA exists)

- Skip MFA step: after username/password, try accessing protected endpoint directly
- MFA brute-force: 6-digit code has 10^6 space — is it rate-limited?
- Response manipulation: does the client decide MFA success? (`{"mfa_required": false}`)

## Phase 7: OAuth2 / OIDC Flaws (if applicable)

- `redirect_uri` bypass: open redirect, localhost bypass
- PKCE not enforced for public clients
- `state` parameter not validated (CSRF in OAuth)
- `nonce` reused

</systematic_approach>
