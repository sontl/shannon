This includes BOLA/IDOR (Broken Object Level Authorization), BFLA (Broken Function Level Authorization), and mass assignment leading to privilege escalation.

<systematic_approach>

## Phase 1: BOLA (Broken Object Level Authorization) — READ

For every endpoint with resource ID in path/body/query:
- Your user's own ID returns 200 (baseline)
- Test other users' IDs — do you get 200 instead of 403/404?

```bash
# Assume your user ID is 42
curl -H "Authorization: Bearer $TOKEN" {{WEB_URL}}/api/users/42   # baseline
curl -H "Authorization: Bearer $TOKEN" {{WEB_URL}}/api/users/41   # IDOR test
curl -H "Authorization: Bearer $TOKEN" {{WEB_URL}}/api/users/1    # admin?
```

## Phase 2: BOLA — WRITE / DELETE

- Can you modify another user's resource?
  ```bash
  curl -X PUT -H "Authorization: Bearer $TOKEN" {{WEB_URL}}/api/users/41 \
    -d '{"email":"pwned@attacker.com"}'
  ```
- Can you delete another user's resource?

## Phase 3: ID Obfuscation Bypass

If IDs are UUIDs or hashes:
- Sequential UUIDs (UUID v1): extract MAC/timestamp — predict next?
- Hash prefixes: are they short enough to collide/brute?
- Parameter pollution: `?id=42&id=41` — which wins?

## Phase 4: BFLA (Broken Function Level Authorization)

Test admin/privileged endpoints with regular user token:
- From discovery, list endpoints under `/admin/*`, `/manage/*`, `/api/internal/*`
- Send with YOUR token
- Record status codes: 200 = BFLA; 403/401 = properly gated

Test HTTP verb manipulation:
- If `DELETE /api/users/42` is blocked, try `POST /api/users/42?_method=DELETE`
- If `PATCH` is blocked, try `PUT` with full object

## Phase 5: Mass Assignment for Privilege Escalation

(Overlaps with the "xss" slot but worth double-checking for authz-critical fields)

On profile/settings update endpoints, add:
- `role`, `is_admin`, `user_type`, `privileges`
- `organization_id`, `tenant_id` (cross-tenant escape)
- `owner_id` (resource ownership)

```bash
curl -X PUT {{WEB_URL}}/api/users/me \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"normal","role":"admin","organization_id":1}'
```

Verify with GET: did the role stick?

## Phase 6: Multi-Tenant Isolation

If the API has tenant/organization/workspace concepts:
- Try accessing resources across tenants by changing tenant/org ID in path, body, or header
- Test headers: `X-Tenant-ID`, `X-Org-ID`, `X-Workspace-ID`

## Phase 7: Resource Enumeration

For public/semi-public resources (projects, files, posts):
- Can you enumerate IDs sequentially?
- Do error messages differ between "not found" and "not authorized"? (Info leak)

## Phase 8: Parameter Tampering

For filtered list endpoints (`GET /api/projects?owner_id=42`):
- Change `owner_id` to someone else — do you see their projects?
- Remove the filter entirely — does it return ALL projects?
- Negative IDs, zero, very large numbers

</systematic_approach>
