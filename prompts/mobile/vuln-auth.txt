<systematic_approach>
## Phase 1: Authentication Mechanism Analysis

1. Read `deliverables/mobile_auth_map.md` for auth token format, session mechanism, and certificate pinning status.
2. Identify the authentication type: JWT Bearer, session cookie, API key, OAuth, biometric + token, basic auth.
3. For JWT tokens: decode header and payload (base64), note algorithm, claims, expiration.
4. For session cookies: note HttpOnly, Secure, SameSite flags, domain, path.
5. Note how the token is stored on the device (SharedPreferences, NSUserDefaults, Keychain, in-memory).

## Phase 2: Transport and Caching Security

1. Check HTTPS enforcement: does the app enforce TLS for all API calls? Are there any plaintext HTTP requests?
2. Check for sensitive data in URL parameters (tokens, passwords in query strings that appear in server logs).
3. Check Cache-Control headers on authenticated responses (should be `no-store`).

## Phase 3: Session Management Testing

1. **Session fixation:** Record session ID before login, check if it changes after login.
2. **Session entropy:** Collect 5+ session tokens, check for patterns or low entropy.
3. **Session expiration:** Wait for token expiry, attempt to use the expired token against the API.
4. **Logout invalidation:** Log out via the app, then replay the pre-logout token in curl — verify server-side invalidation.
5. **Concurrent sessions:** Log in on two devices simultaneously, check if both sessions remain valid.
6. **Background token refresh:** Observe if the app silently refreshes tokens — is the refresh endpoint rate-limited?

## Phase 4: Authentication Bypass Attempts

1. **Missing auth check:** Access protected API endpoints without any auth header/cookie via curl.
2. **Empty/null tokens:** Send `Authorization: Bearer ` (empty), `Authorization: Bearer null`.
3. **Algorithm confusion (JWT):** If HS256, try `alg: none` with empty signature. Try RS256→HS256 confusion if public key is discoverable.
4. **Token manipulation:** Modify JWT claims (change user ID, role, email) and re-sign with common weak secrets (`secret`, `password`, `key`, app name).
5. **Password reset flow:** Check if reset tokens are predictable, reusable, or don't expire.

## Phase 5: Mobile-Specific Authentication Tests

1. **Biometric bypass:** Use Appium to attempt navigation past biometric screens without completing authentication. Check if the biometric check is enforced server-side or only client-side.
2. **Deep link auth bypass:** Test whether deep link URLs allow navigation to authenticated screens without a valid session (e.g., `app://dashboard` while unauthenticated).
3. **Intent/URL scheme injection:** Test if intents or custom URL schemes can pre-populate login credentials or skip authentication steps.
4. **Rooted/jailbroken detection bypass:** If the app checks for root/jailbreak, determine if bypassing this check opens additional attack surface.
5. **Token in SharedPreferences/NSUserDefaults:** If the auth map shows token stored in unencrypted storage, document the risk and note whether token extraction from a backup is feasible.

## Phase 6: Credential Testing

1. **Default credentials:** Test common admin credentials (admin/admin, admin/password).
2. **Rate limiting:** Test if login endpoint has rate limiting (5+ rapid failed attempts).
3. **Account enumeration:** Compare error messages for valid vs invalid usernames.
4. **Response timing:** Measure response times for valid vs invalid usernames (timing oracle).

## Phase 7: Login/Signup Response Analysis

1. Check for user enumeration via different error messages ("user not found" vs "wrong password").
2. Check password policy enforcement (minimum length, complexity requirements).
3. Check for CAPTCHA or anti-automation on login/signup.
4. Check for account lockout policy.
</systematic_approach>
