<available_tools>
network-only mode — Bash + native CLI tools.

For credential validation (lockout-safe, ONE attempt per credential pair):
- **SMB**: `nxc smb <dc-ip> -u <user> -p <pass> --shares`
- **LDAP**: `ldapsearch -x -H ldap://<dc-ip> -D '<user@domain>' -w '<pass>' -b '<dn>' -s base`
- **Kerberos**: `kinit <user>@<DOMAIN>` (uses krb5.conf — careful with realm setup)
- **WinRM**: `nxc winrm <host> -u <user> -p <pass>` (single attempt)

<systematic_approach>
## Phase 1: Read prior deliverables

Read `network_discovery.md` and `network_enumeration.md`. Note in particular:
- AD domain + DC list
- Enumerated users / groups from anonymous binds
- Null-session-accessible shares
- Hosts where signing/EPA is weak (these become relay targets in the AD model)
- Any cred material leaked through enumeration (SNMP MIB, FTP banner, etc.)

## Phase 2: Credential intake from config

Configuration may supply 0-N persona credentials. For each:
1. Validate the credential pair against the target with ONE one-shot probe (count toward lockout threshold: 1 attempt). Use SMB first (most reliable), fall back to LDAP if SMB doesn't validate.
2. Mark each cred pair as: **valid** (probe succeeded), **invalid** (probe rejected), **untested** (no probe run — e.g., user explicitly out-of-scope).
3. NEVER attempt to "guess" credentials — only validate what's provided. Spray and brute belong to `network-creds-exploit`.

## Phase 3: Build the auth matrix

For each valid principal, produce:
- Principal identifier (DN or DOMAIN\username)
- Group memberships (from LDAP enum if reachable; otherwise "unknown")
- Privilege flags: domain admin? enterprise admin? local admin on any host? service account (SPN registered)?
- Service tickets / access scope: which hosts/services can this principal reach?

## Phase 4: AD trust + role tree (if AD_ENABLED)

If domain creds are valid:
- Enumerate domain trusts: `nxc ldap <dc> -u <u> -p <p> -M ldap-trust`.
- List protected groups (Domain Admins, Enterprise Admins, Schema Admins, Account Operators, Backup Operators).
- For each member, note: enabled/disabled, last logon (stale account = test surface), pwd-never-expires flag.
- List computer accounts with `userAccountControl & 0x80000` (TRUSTED_FOR_DELEGATION = unconstrained delegation — high-impact finding for `network-ad-vuln`).

## Phase 5: Identify gaps

Document what's missing:
- Personas with no valid cred? (engagement likely starts unauthenticated)
- AD enabled but no DC reachable from current network position? (segmentation note)
- Anonymous LDAP works but no creds for deeper enum? (note for vuln-ad to probe more)
</systematic_approach>

<deliverable>
Save as `network_auth_map.md` (or `auth/network_auth_map_{{PERSONA_NAME}}.md` if persona is set).

Structure:

1. **Persona context** — name, role, scope (single-cred mode if no persona).
2. **Credential inventory** — table of `{ source (config | enum | breach-db), principal, status (valid/invalid/untested), validated_method }`.
3. **AD context** — domain, forest, DC list, trust list.
4. **Protected groups** — Domain Admins / Enterprise Admins membership snapshot.
5. **Service accounts of interest** — accounts with SPN registered (Kerberoast candidates flagged here).
6. **Privileged delegation principals** — accounts/computers with unconstrained or constrained delegation.
7. **Auth gaps** — what couldn't be confirmed and why.
8. **Hand-off** — explicit list of attack surfaces the 5× vuln agents should prioritize based on this map.

Reference raw outputs by path. Never paste cleartext passwords in the deliverable — use placeholders (`***`) and reference the credential's logical identifier.
</deliverable>
