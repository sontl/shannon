<systematic_approach>
Execute the phases below in order. Skip a phase if its scope is empty for this engagement (e.g., no public-facing assets in pure-internal mode).

## Phase 1: Scope Confirmation (always)

1. Read the `Network scope` block in `<target>` above. List every entry under `Targets` and `Excludes`.
2. For each target, classify as: single IP, CIDR range, hostname (FQDN), or wildcard pattern.
3. Resolve hostnames to IPs (`dig +short`). Add IPs to your working list. If a hostname resolves to multiple IPs, document each.
4. **Reject any target in the excludes list.** If a hostname resolves to an IP that's in the excludes list, drop the IP and note it.

Output: a normalized list of in-scope IPs and CIDRs you will actually probe.

## Phase 2: Passive Recon (external mode and hybrid mode)

Skip this phase if `ENGAGEMENT_MODE == internal`. For external and hybrid, gather public intel without sending packets to the target's network.

1. **WHOIS / ASN** — for each target IP, run `whois <ip>` to identify the owning ASN and netblock. Then `bgpq4 -l prefix <ASN>` to list all prefixes announced by that ASN. Hint: M&A history often leaves forgotten netblocks that are still listed here.
2. **DNS** — for the AD domain (if `AD_ENABLED`) and any FQDN in scope:
   - `dig any <domain>`
   - NS records (which DNS provider tells you the maturity of the org)
   - MX records (Microsoft 365 vs Google vs on-prem Exchange = very different attack surface)
   - SPF/DMARC TXT records (often disclose legacy IP ranges)
   - Attempt zone transfer: `dig axfr @<ns> <domain>` (rare but still happens).
3. **Certificate Transparency** — `curl -s https://crt.sh/?q=<domain>&output=json | jq '.[] | .name_value' | sort -u` for internal hostnames that ever appeared on a public cert.
4. **Subdomain enum** — `subfinder -d <domain>` (passive only at this phase; active resolution comes later).
5. **OPTIONAL: Shodan / Censys** — if API keys are present in env (SHODAN_API_KEY, CENSYS_API_ID/SECRET), pull passive port/banner data. Skip cleanly if absent.

Output: `deliverables/network_discovery_public_intel.md` (or include as a section in the main deliverable).

## Phase 3: Active Host Discovery (always)

1. Use `nmap -sn <scope>` for ICMP/ARP-friendly subnets to identify live hosts. For internal segments where ARP works, also try `arp-scan --interface=eth0 <subnet>`.
2. For Internet-facing scope, ICMP is often blocked — fall back to TCP SYN to common ports (`nmap -PS22,80,443,445,3389 -sn <scope>`).
3. Document any subnet where your probe succeeds (subnet is reachable) vs fails (segmentation in effect — note this).

Output: `hosts_alive.json` (just a list of `{ ip, hostname?, response_method }`).

## Phase 4: Port Discovery (always)

Two-stage strategy: fast wide scan → confirmation.

1. **Wide scan.** `naabu -host <hosts_alive> -p - -rate 5000 -o /tmp/naabu.json` for all 65k TCP. For large CIDR scope use `masscan` with `--rate 10000`. Tune rate down if you observe target stability issues.
2. **Service detection on found ports.** `nmap -sV -sC -p $(jq -r '.[].port' /tmp/naabu.json | sort -u | paste -sd,) -iL hosts_alive.txt -oX /tmp/nmap.xml`. Parse the XML — keep service name, version, banner, OS guess.
3. **UDP top-100.** `nmap -sU --top-ports 100 -iL hosts_alive.txt` — UDP is slow but SNMP (161), NTP (123), and DNS (53) are too valuable to skip.

Output: structured per-host service inventory.

## Phase 5: Categorize and Hand Off

Group findings by service family so downstream enumeration knows what to look at:
- **AD signals**: 88 (Kerberos), 389/636 (LDAP/LDAPS), 445 (SMB), 3268 (Global Catalog), 53 (DNS hosting the AD zone). Even one of these on an Internet-facing host is unusual and worth flagging.
- **Web/admin panels**: 80, 443, 8080, 8443, 8000, 9000, 5985 (WinRM HTTP), 5986 (WinRM HTTPS).
- **Database**: 1433 (MSSQL), 3306 (MySQL), 5432 (PostgreSQL), 27017 (MongoDB), 6379 (Redis).
- **Remote admin**: 22 (SSH), 3389 (RDP), 5900 (VNC), 161 (SNMP), 623 (IPMI).
- **File services**: 21 (FTP), 2049 (NFS), 873 (rsync).
- **Other interesting**: 25 (SMTP — possible auth surface), 1099/8009 (RMI/AJP — historic CVEs), 8000-9000 range (often misconfigured admin tools).

## Phase 6: Cloud Asset Detection (informational only)

If you detect cloud-hosted assets (e.g., reverse DNS resolves to `*.compute.amazonaws.com`, `*.azure.com`, `*.googleusercontent.com`, or IMDS endpoints reachable from within `100.64.0.0/10` / `169.254.169.254`), DOCUMENT them in a separate "Cloud Assets Detected" section, then explicitly mark them **OUT OF SCOPE FOR THIS TIER**.

Rationale: cloud pentest (IMDS abuse, IAM role chaining, S3 bucket attacks, Azure synthetic delegation) is a separate discipline with separate tooling and methodology. Gandalf's network tier intentionally does not pursue cloud-specific attacks — that's a future `cloud-graybox` tier (see `docs/research/network-pentest.md` § "Cloud — quyết định scope").

Do not run AWS/Azure/GCP CLI commands, do not probe IMDS, do not test cloud-specific APIs. Just note "Cloud assets detected: [list]; deferred to cloud tier".
</systematic_approach>
